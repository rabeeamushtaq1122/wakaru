Title: Harden named require recovery against unsafe CommonJS boundaries

Improve named-member recovery for top-level CommonJS imports without changing runtime behavior.

When converting a top-level binding such as `var UIBase = require("./dep.js").UIBase` into a named import, recover it only when the property name is a valid JavaScript identifier and the binding's recovered value cannot be invalidated by a provider-member mutation. Treat assignments, compound assignments, updates, deletes, and for-in/for-of assignment heads as mutations. An earlier proven binding may remain recoverable when a later provider mutation is preserved as CommonJS code rather than folded into the import.

Preserve the original CommonJS form when the provider member can change, when the property name cannot be represented as an identifier, or when the candidate is an early read from the current module's own CommonJS export surface. In particular, do not partially cross the CommonJS boundary for a self-module read that occurs before its exported member is initialized.

Keep existing safe recovery behavior for valid, unmutated dependency members and for already-supported self-module export surfaces. Scope and binding checks must distinguish the global `require` from locally shadowed bindings, and the implementation must continue using the repository's existing pipeline and import-generation conventions.

Add focused tests for invalid identifier property names, every supported provider-member mutation form, early self-module reads, and a valid named import that remains recoverable even when a later provider mutation is preserved.
